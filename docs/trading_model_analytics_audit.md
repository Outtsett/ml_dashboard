## 2. Per-model deep dive

### 2.1 `trading_model` — MNQ 1m Range/Swing Transformer (maturity 4/5)

**Architecture**
- Two-stream pure Transformer: price `Linear(4->112)` + sinusoidal PE; volume `Linear(1->16)` no PE; concat to `d=128`.
- `TransformerEncoder` 4L / 4H / `d_ff=512`, mean-pool, single configurable head.
- 128-bar OHLCV window, ~796K params at defaults. CNN/VQ/CLS removed.
- Active head: `range_class` next-close range-bucket classifier (K=21, 2pt bucket).
- Backup head: `barrier_class` swing direction (triple-barrier path retained but deprecated for autocorrelated-label leak).

**Headline metrics**
- `within2pt_acc` — primary (range head: next-close within ±2 points)
- `profit_factor` — secondary (swing head: gross_profit / gross_loss from cost-aware sim)
- Auxiliary: `directional_accuracy`, `mae_pts`, `sharpe_per_trade`, `gated_sharpe` (q_med / sigma confidence-gated)

**Evaluation scripts**
- `src/ml/cnn_transformer/range_evaluate.py` — 18+ metrics: `exact_acc`, `within{2,4}pt_acc`, `mae_pts`, `directional_accuracy`, `n_trades`, `total_pnl_usd`, `win_rate`, `profit_factor`, `sharpe_per_trade`, `gross_profit_usd`, `gross_loss_usd`, `trade_rate`, gated/ungated variants
- `src/ml/cnn_transformer/swing_evaluate.py` — multi-bar swing sim (entry/exit on prediction flip), `profit_factor`, `sharpe_per_trade`, `mean_hold_bars`, `pct_above_cost`
- `src/ml/cnn_transformer/walk_forward.py` — expanding-window CV, 6-month test folds, 120-bar purge
- `src/ml/cnn_transformer/direction_evaluate.py` — backup-head metrics
- `src/ml/cnn_transformer/evaluate.py` — generic eval entry-point
- HPO: `scripts/train_range_hpo.py`, `scripts/train_swing_hpo.py`, `scripts/train_direction_hpo.py` (Optuna TPE; SQLite-backed studies under `optuna_studies/{head}_{symbol}_{timeframe}.db`)
- Sweeps: `sweeps/{range,swing}.yaml` + `scripts/sweep_trial_{range,swing,direction}.py` (native W&B sweeps)
- Audits: `scripts/audit_{dataset_alignment,boundary_mask,gating_threshold}.py` (existing leakage / gate sanity checks)

**Persistent outputs**
- `data/analysis/range_hpo/` — HPO outputs
- `data/models/MNQ_1m_range_transformer/checkpoint_range.pt` — active checkpoint
- `data/tableau/*.csv` — dashboard extracts (regenerated by `scripts/build_tableau_extract.py`)
- `optuna_studies/*.db` — resumable HPO studies

**W&B integration**
- Projects: `mnq-1m-range`, `mnq-1m-swing`, `mnq-1m-barrier` (one per head)
- Per-trial runs grouped by `study_name`, named `f"trial-{n:03d}-..."`
- Artifact lineage: `dataset-manifest -> cost-model -> hpo-results-{head} -> model-{head}` with `[latest, best]` aliases; `best` auto-promoted on within2pt_acc / profit_factor improvement
- `protocol.py::emit_metric` forwards to `wandb.log` when `WANDB_FORWARD=1` with `train_/val_/step_/gpu_` -> `train//val//step//system/` namespace mapping
- `wandb.define_metric(...summary="max")` for fold-level aggregation
- Tests: `tests/test_protocol_wandb_forward.py`

**Dashboards / viewers**
- `scripts/dashboard.py` — Dash/Plotly, 6 panels (swing-period heatmap, HPO fold-stability heatmap, training convergence, HPO leaderboard, OOS probability distribution, run-summary table)
- `scripts/training_monitor.py` — terminal UI (dark theme, `ACCENT=#22d3ee`)
- `scripts/dash_training_viewer.py` — additional Dash viewer
- `scripts/prediction_viewer.py` — candlestick + swing predictions (zigzag pivot detection over `oos_predictions.npz`)
- `scripts/build_tableau_extract.py` — regenerates `data/tableau/*.csv` from W&B
- Analyses: `scripts/analyze_snr_by_timeframe.py`, `scripts/find_optimal_swing_periods.py`

**Gaps (prioritized)**
1. **No per-regime breakdown** — no clustering or classification of market regimes (trend vs mean-revert; volatility / volume / time-of-day buckets); within2pt_acc and profit_factor not decomposed by regime
2. **No calibration plots** — no predicted vs realized delta scatter; no quantile calibration curves; no reliability diagram for the gated trade gate (`q_med / sigma`)
3. **No slippage / commission sweep** — trade sim uses entry/exit at `close[i]` (instantaneous fills); cost model is single-point, never swept
4. **No feature attribution** — Transformer attention weights not exported; no per-primitive importance rank; no primitive×primitive interaction heatmap
5. **No per-bucket accuracy** — `within2pt_acc` is aggregate; per-bucket precision/recall (centre vs tail buckets) not logged
6. **No walk-forward decay plot** — fold-by-fold test metric trend over time not visualized; model decay invisible until manual inspection
7. **No bootstrap CIs** — headline metrics are point estimates; no block-bootstrap interval per fold or aggregated
8. **No automated label-leakage check beyond `purge_bars`** — a single hard-coded constant (120 bars) is the only safeguard; no automated check that the prediction horizon never crosses fold boundaries
9. **No gated-Sharpe calibration test** — the confidence gate is in the metric definition but its calibration (expected vs observed win rate at each confidence percentile) is not tested

### 2.3 `forexmodel` — Differentiable LSTM Sharpe Trader (maturity 2/5)

**Architecture**
- 2-layer LSTM, 128 hidden, ~215K params; LayerNorm input, GELU head projection, Tanh final output
- Target: EURUSD 1m bars
- Output: position signal in `[-1, 1]` per bar
- Loss: negative annualized Sharpe ratio (end-to-end differentiable training on strategy returns after transaction costs)
- 15-feature pipeline (RSI, SMA, ATR, log returns, range, body, volume)

**Headline metrics**
- Annualized Sharpe — primary
- Profit factor, max drawdown, win rate, total return, cost impact, position autocorrelation, average position duration, trade count

**Evaluation scripts**
- `scripts/train.py` — walk-forward trainer with OOS evaluation; Lopez de Prado expanding-window folds (default 6); 2-month validation windows; 5-day purge gaps; stride sampling (256 bars for train overlaps, non-overlapping validation)
- `scripts/verify_setup.py` — environment / config sanity check
- `src/forexmodel/data/loader.py` — EURUSD bar loader
- `src/forexmodel/evaluation/metrics.py` — 9 metrics from position array

**Persistent outputs**
- `checkpoints/fold_{n}/best.pt` per fold (state_dict + config + metrics)
- **No JSON/CSV reports.** All metrics print to stdout only.

**W&B integration**
- **Documented but NOT implemented.** `docs/wandb-integration.md` describes per-fold runs grouped under `walk-forward-v1`, the artifact pipeline, model registry stages, NaN/gradient alerts, Optuna+W&B sweeps. None of this is wired into `scripts/train.py`. This drift between docs and reality is itself a gap.

**Dashboards / viewers**
- **None.** Document presumes the W&B UI but the integration that would populate W&B does not exist.

**Gaps (prioritized)**

2. **No offline metric persistence** — stdout only; no per-fold JSON/CSV report; multi-run comparison requires manual scraping
3. **No fold-comparison export** — without W&B and without JSON reports, fold-by-fold comparison has no surface
4. **No IS-vs-OOS overfitting check** — train Sharpe vs val Sharpe gap not printed or logged
5. **No walk-forward cumulative-return plot** — only per-fold summary; no equity curve over the full walk-forward span
6. **No feature importance** — Sharpe loss is monolithic; per-feature contribution never decomposed
7. **No regime analysis** — performance under trending vs mean-reverting EURUSD regimes never measured
8. **No sweep results despite Optuna+W&B documented** — Optuna integration exists in spec only
9. **No calibration metrics** — no correlation analysis between position magnitude and realized return

### 2.4 `dqn_trading` — Dueling Double DQN (maturity 2/5)

**Architecture**
- Dueling Double DQN in LibTorch (C++ core); configurable 2-4 hidden layers, 64-512 units
- Discrete action space: hold / long / short
- State: flattened feature window (8 features × `window_size`) + position one-hot + unrealized PnL
- Reward: strategy PnL per episode

**Headline metrics**
- Sharpe per episode — primary
- Total return, max drawdown, win rate, trade count, mean reward, episode rewards trend, average loss

**Evaluation scripts**
- `tuning/train.py` — standalone trainer (200 episodes default); loads JSON params or Optuna best params
- `tuning/optimize.py` — Optuna TPE + median pruner (100 trials default); tunes hidden_size, num_layers, window_size, lr, gamma, epsilon_decay, batch_size, buffer_size, target_update_freq, transaction_cost; objective = `0.7 * Sharpe + 0.3 * stability − drawdown_penalty`
- `scripts/evaluate.py` — held-out inference; total return, Sharpe, MDD, win rate, num trades, action distribution (hold % / long % / short %)

**Persistent outputs**
- `checkpoints/dashboard_model` — binary LibTorch checkpoint
- `checkpoints/optuna_results.json` — best score, best params, n_trials, n_pruned (no per-trial breakdown)
- Equity curves and action traces returned in-memory only — never persisted

**W&B integration**
- **Not integrated.** Violates global mandatory rule.

**TensorBoard integration:** Not integrated.

**Dashboards / viewers**
- `dashboard/server.py` (Flask) + `dashboard/templates/index.html` (Chart.js) — live SSE
- **Train tab:** real-time config panel; progress bar; 6 metric cards (Sharpe, episode PnL, max DD, trades, epsilon, avg loss); 4 line charts (episode rewards, episode PnL bar, training loss, epsilon decay); action-distribution donut; equity curve (latest episode); replay-buffer utilization bar; log panel (last 200)
- **Operate tab:** 5 metric cards (total return, Sharpe, MDD, win rate, num trades); price chart with long/short markers; action donut; full-run equity curve; playback-speed slider + step counter
- No static export, no historical persistence

**Gaps (prioritized)**
1. **No W&B** — global rule violation
2. **No train/val split** — only training metrics tracked; no held-out validation analytics
3. **Optuna results lack per-trial breakdown** — JSON has only best + counts; no per-trial table
4. **No drawdown duration / recovery time** — only max drawdown; recovery profile unknown
5. **Flat transaction cost** — single scalar, no slippage / queue model, no cost sensitivity sweep
6. **No per-action reward breakdown** — average reward when holding vs long vs short never reported
7. **No regime detection** — no trending vs ranging classification of market state
8. **No feature/state attribution** — flattened state vector has no saliency / attention analysis
9. **No off-policy evaluation** — no counterfactual analysis of alternative actions
10. **Dashboard metrics not persisted** — live-only; cannot review prior sessions after the process exits

## 4. Universal gaps (true of every standalone model)

These are not per-model issues — every standalone model is missing all of them:

- **Calibration analysis** — no model exposes a reliability diagram or quantile-calibration curve
- **Regime breakdown** — no model decomposes its headline metric by trend / mean-revert, volatility bucket, volume bucket, or time-of-day
- **Feature / attention attribution** — every model produces useful internal signals (Transformer attention weights for `trading_model`, feature-attention for `primitives_discovery`, gradient saliency for `forexmodel`, Q-value attribution for `dqn_trading`); none of them are extracted or rendered
- **Bootstrap confidence intervals** — every headline metric is a point estimate; no block-bootstrap or stationary-bootstrap interval
- **Cross-model comparison** — there is no apples-to-apples Sharpe / profit_factor / MDD matrix across the four standalone models, despite all of them targeting trading

The natural home for all five of these is the `ml_dashboard` UI, where the schema and routing already exist — but `models.json` is empty so nothing is wired in.

## 6. Metric naming standard

The current metric names across all five repos read as code identifiers, not as questions the metric answers. `within2pt_acc`, `dir_auc`, `mag_loss`, `gated_sharpe`, `cost_adj_sharpe`, `pct_above_cost`, `q_med` — each requires a decoder ring before the dashboard means anything. When 30+ metrics scroll past on a model row, the user has to translate every one into "what is this telling me?" before they can act.

### Principle

A metric name should answer the question "what is this measuring?" without prose explanation. Three rules, in order:

1. **Intent over implementation.** Name what the number tells you, not how it was computed. `direction_correct_rate` says what it shows; `dir_acc` is an implementation detail.
2. **Units explicit when they matter.** `prediction_error_points` beats `mae_pts`. `drawdown_pct` beats `mdd`.
3. **Industry-standard names retained when truly standard.** `sharpe_per_trade`, `profit_factor`, `win_rate` are fine — every quant reader knows them. `auc` is borderline; prefer `direction_auc` so the head is named.

Tyler's existing naming rule from `~/.claude/CLAUDE.md` applies: **minimal, operational — domain + component, no descriptions/metaphors.** That rule is preserved here. The fix is not to make names longer — `within2pt_acc` is already short — but to swap implementation tokens for intent tokens (`acc` -> `rate`, `mag` -> `magnitude`, `dir` -> `direction`).

### Headline vs detail tier

Most "overwhelm" comes from showing every metric at the same visual weight. Two tiers, enforced in the dashboard's `metric_declarations` SSE event and the Semantic Standard `group` field:

- **Headline (always shown on a model's row):** the one metric that decides "is this model good?" — `close_hit_2pt_rate` for the range head, `sharpe_after_costs` for everything that trades, `direction_auc` for primitives_discovery, `sharpe_per_trade` for forexmodel and dqn_trading.
- **Detail (drill-down only):** the rest.

The `metricRegistry.json` proposal below carries the tier per metric so the UI can hide detail by default.

### The metric key — every metric self-describes

Every metric, in the registry and in the dashboard, has a **metric key** with five fields:

| Field | What it answers |
|---|---|
| `intent` | What the number is showing — one sentence in the user's voice ("how often the model is right") |
| `target` | The good / acceptable / bad numeric ranges |
| `direction` | `up` (higher = better), `down` (lower = better), or `flat` (descriptive, no preference) |
| `levers` | The 1-3 actionable knobs to move this metric in the desired direction |
| `applies_to` | Which models surface this metric |

The dashboard renders the `intent` as the metric's caption, the `target` as a coloured band on the gauge, and the `levers` as a hover tooltip. No more decoder-ring naming, no anonymous numbers, no unexplained scores.

The categories below are named by the question they collectively answer. Each category is a contract: every metric inside it is comparable to its siblings — same direction, comparable units, same kind of lever moves them.

### Category A — Correctness (how often is the prediction right?)

| Metric | Was | Intent | Target (good / ok / bad) | Direction | Levers |
|---|---|---|---|---|---|
| `bucket_match_rate` | `exact_acc` | Fraction of bars where predicted bucket equals true bucket | depends on K; with K=21 baseline is 1/21 ≈ 0.048 | up | sharpen distribution; lower K; reduce label noise |
| `close_hit_2pt_rate` | `within2pt_acc` | Fraction of bars where realized close lands within ±2pt of bucket centre | >0.45 / 0.35-0.45 / <0.30 | up | larger model; more relevant features; tighter buckets |
| `close_hit_4pt_rate` | `within4pt_acc` | Same, ±4pt tolerance | >0.65 / 0.50-0.65 / <0.45 | up | same as above |
| `direction_correct_rate` | `dir_acc` / `directional_accuracy` | Fraction of bars where predicted up/down matches realized | >0.55 / 0.50-0.55 / <0.50 | up | better directional features; class balancing; longer label horizon |
| `direction_auc` | `dir_auc` | ROC-AUC of the long/short/flat head | >0.60 / 0.55-0.60 / <0.52 | up | features; class balancing |
| `forward_return_auc` | `fwd_auc` | ROC-AUC of the forward-return head | >0.58 / 0.52-0.58 / <0.52 | up | longer label horizon; better features |

### Category B — Error magnitude (how wrong when wrong?)

| Metric | Was | Intent | Target | Direction | Levers |
|---|---|---|---|---|---|
| `prediction_error_points` | `mae_pts` | Mean absolute error in MNQ points | <2 / 2-4 / >5 (relative to bucket size) | down | model capacity; lower lr; longer training |
| `magnitude_squared_error` | `mag_loss` | MSE on the magnitude head | depends on output normalization — track relative to baseline | down | normalize target; regularize; more capacity |
| `quantile_median` | `q_med` | Median of predicted distribution | should equal observed median when calibrated | flat | quantile loss; better tail features |

### Category C — Profit and loss (does trading on this model make money?)

| Metric | Was | Intent | Target | Direction | Levers |
|---|---|---|---|---|---|
| `pnl_usd_total` | `total_pnl_usd` | Net P&L over the eval window | net positive | up | improve direction; tighter exits |
| `win_rate` | _(keep)_ | Fraction of trades closed positive | >0.55 / 0.50 with skewed payoff / <0.45 | up | raise entry threshold; regime filter |
| `profit_factor` | _(keep)_ | Gross profit / gross loss | >1.5 / 1.0-1.5 / <1.0 unprofitable | up | bigger winners; tighter stops |
| `gross_profit_usd` | _(keep)_ | Sum of winning trade P&L | larger than `gross_loss_usd` | up | direction; position sizing |
| `gross_loss_usd` | _(keep)_ | Sum of losing trade P&L | smaller than `gross_profit_usd` | down | tighter stops; regime filter |
| `bars_with_edge_pct` | `pct_above_cost` | Fraction of bars where predicted edge exceeds expected cost | >0.10 typical for selective | up | stronger edge per bar; lower-cost regime |

### Category D — Risk (how dangerous is the model's profit?)

| Metric | Was | Intent | Target | Direction | Levers |
|---|---|---|---|---|---|
| `drawdown_max_pct` | `maxDrawdown` / `max_drawdown` | Worst peak-to-trough decline as % of equity | <10% / 10-20% / >30% dangerous | down | position sizing; regime filter; stop-loss |
| `sharpe_per_trade` | _(keep)_ | Risk-adjusted return per trade | >0.10 / 0.05-0.10 / <0.03 | up | tighter exits; lower per-trade variance |
| `sharpe_after_costs` | `cost_adj_sharpe` | Annualized Sharpe after subtracting cost model | >1.5 / 0.8-1.5 / <0.5 | up | reduce trade frequency; widen required edge |
| `sharpe_high_confidence_only` | `gated_sharpe` | Sharpe restricted to bars where the confidence gate fires | should exceed `sharpe_after_costs` | up | improve confidence-head calibration |

### Category E — Trade frequency (how often, how long does it trade?)

| Metric | Was | Intent | Target | Direction | Levers |
|---|---|---|---|---|---|
| `trade_count` | `n_trades` | Trades executed in the eval window | depends on strategy (too few = no edge captured; too many = cost drag) | flat | confidence-gate threshold |
| `trades_per_bar` | `trade_rate` | Trades per OHLCV bar | 0.01-0.05 typical for selective | flat | confidence gate |
| `hold_bars_avg` | `mean_hold_bars` | Average bars held per trade | should match the prediction horizon | flat | exit rule design |

### Category F — Training convergence (is training going well?)

| Metric | Was | Intent | Target | Direction | Levers |
|---|---|---|---|---|---|
| `train_loss` | _(keep)_ | Loss on the training set | monotonic decrease | down | optimizer; lr schedule |
| `val_loss` | _(keep)_ | Loss on the validation set | should track `train_loss`; the gap is overfit | down | regularization; dropout; smaller model |
| `val_accuracy` | _(keep)_ | Validation accuracy | exceeds class-prior baseline by a margin | up | features; capacity |
| `macro_f1` | _(keep)_ | Macro-averaged F1 across classes | balanced precision/recall across all classes | up | class balancing; focal loss |
| `step_learning_rate` | `step_lr` | LR at this gradient step | follows configured schedule | flat | lr-schedule design |
| `grad_norm_pre_clip` | `step_grad_norm_pre_clip` | L2 norm of gradients before clipping | stable, no spikes; spikes mean instability | flat | grad clipping; lower lr; better init |
| `samples_per_sec` | `step_samples_per_sec` | Training throughput | maximize for given hardware | up | batch size; dataloader workers; mixed precision |
| `epoch_time_sec` | _(keep)_ | Wall-clock seconds per epoch | as low as possible without hurting convergence | down | same as above |

### Category G — Resource cost (what does training cost in compute?)

| Metric | Was | Intent | Target | Direction | Levers |
|---|---|---|---|---|---|
| `gpu_mem_used` / `gpu_mem_total` | _(keep)_ | VRAM bytes used / total | **target 50-60% (Tyler's rule); never 100%** | flat (band) | batch size; model size; gradient accumulation |
| `peak_memory_mb` | _(keep)_ | Peak host RAM during training | < available RAM with headroom | down | dataloader settings; prefetch |
| `average_cpu_pct` | _(keep)_ | Average CPU utilization | not pinned at 100% (leaves OS headroom) | flat | `num_workers ≤ cpu_count // 3` (max 4) |

| Metric | Was | Intent | Target | Direction | Levers |
|---|---|---|---|---|---|
| `quality_score` | `qualityScore` | **Composite formula undocumented.** Either define inputs in `src/shared/schema.ts` or rename to the underlying numeric (proposed: `oos_sharpe_decay`). | n/a until defined | up | n/a until defined |
| `eval_grade` | `evaluationGrade` | **Scale undocumented.** Letter? 0-100? Rubric? Either define or replace with underlying numeric. | n/a until defined | up | n/a until defined |
| `oos_sharpe_decay` (proposed) | n/a | Ratio: `sharpe_after_costs` on recent N bars / on training window | >0.70 stable / 0.50-0.70 drifting / <0.50 broken | up | retrain cadence; regime filter; feature staleness check |

### Category I — DQN-specific (Q-learning health)

| Metric | Was | Intent | Target | Direction | Levers |
|---|---|---|---|---|---|
| `episode_reward_avg` | `mean_reward` | Average reward across recent episodes | trending up over training | up | reward shaping; replay-buffer size; target-update frequency |
| `episode_reward_series` | `episode_rewards` | Per-episode reward time series | low variance once converged | flat (descriptive) | reward shaping; epsilon-decay schedule |
| `epsilon` | _(keep)_ | DQN exploration rate | follows configured decay schedule | flat | epsilon-decay tuning |

### W&B namespace alignment

The existing `protocol.py::emit_metric` mapping (`train_/val_/step_/gpu_` -> `train//val//step//system/`) is correct in principle. Apply the new metric names within those namespaces:

- `train/loss`, `train/learning_rate`
- `val/close_hit_2pt_rate`, `val/sharpe_after_costs`
- `step/grad_norm_pre_clip`, `step/samples_per_sec`
- `system/gpu_mem_used`

This keeps W&B runs queryable by intent (`val/sharpe_after_costs.max()`) instead of by abbreviation (`val/cost_adj_sharpe.max()`).

### Promotion to Tier-1 recommendation

This rename is now **Tier 1, item 0** in the recommendation list — it is a prerequisite for the cross-model comparison work in Tier 2, because the comparison page needs every model's headline metric to share a vocabulary. Without the registry, the matrix's columns are `within2pt_acc | dir_auc | sharpe | sharpe` and require a footnote explaining each cell. With the registry, the matrix's primary column is `headline_metric` and every model self-describes what its headline measures.
